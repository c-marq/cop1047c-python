B · Any type, stubs, ifs and loops inside

Ch 6 Part 2 · zyBooks 6.3, 6.4, 6.6, 6.7 · One function can take any type its body can handle. A stub plans a function with pass. Ifs and loops go inside functions as usual, with return at the end.

Quick refresher

Python doesn't ask what type a parameter is: any value gets in, as long as the body can use it (len() works on strings, lists and dictionaries, but not on numbers). A stub is a real header with pass as the body; it runs and returns None. Inside a function, an if/elif ladder can return a different label from each branch, and a loop can build a total that you return AFTER the loop.

def get_length(x):            # any type with a length
    return len(x)

def save_order(item):         # a stub: plan now, write later
    pass

print(get_length("Miami"))    # 5
print(get_length([1, 2, 3]))  # 3
print(save_order("cafecito")) # None

A Little Havana tour guide keeps three kinds of data: a list of stops, the name of the neighborhood, and a dictionary of cafecito-window prices. Write ONE function named count_items() with one parameter that returns len() of whatever it receives. Call it three times, once for each value in the plan, and print each result with the labels shown in the plan.

How to think about the plan

  1. This is dynamic typing: one function, three different types. The function never checks the type.
  2. len() works on a list (counts items), a string (counts characters, spaces included) and a dictionary (counts keys).
  3. The function's whole body is one return line. The main program does the printing.
  4. Copy the three given lines exactly, so your numbers match the target.

Think first

  • What type is each of the three values?
  • What will len() count for each one?
  • Should the function print or return? Who prints the labels?

Watch out

Any type gets in, but the body still has to work on it. count_items(1.50) stops with TypeError: object of type 'float' has no len(). A dictionary's len counts its keys, not its prices.

You and a teammate are planning a ventanita ordering app. Before anyone writes the bodies, you agree on three functions: take_order(item), get_total(price, qty) and print_receipt(total). Write all three as stubs with pass. Then replace ONLY get_total's pass with a real body that returns price times qty. In the main program, call take_order("cafecito") and get_total(1.50, 3), store both results, print them, and call print_receipt(total).

How to think about the plan

  1. A stub is the real header (name and parameters) with pass as the body. Python needs pass because a body can't be empty, and a comment doesn't count.
  2. Run the program with all three as stubs first. It runs top to bottom, and every call hands back None.
  3. Then fill in only get_total. The other two stay stubs, and the program still runs.
  4. take_order is still a stub, so what it returns is None. That's the expected output, not a bug.

Think first

  • What do you expect a stub to return?
  • Why does Python need pass instead of a comment?
  • Which of the three functions do you fill in, and what does it return?

Miami's UV index is often 10 or higher. Write uv_advice(uv) that returns advice: 11 or more is "Extreme: stay in the shade", 8 or more is "Very high: sunscreen and a hat", 6 or more is "High: sunscreen", 3 or more is "Moderate: sunglasses", and anything lower is "Low: enjoy the beach". Then use a for loop over this week's readings (given in the plan) and print each reading with its advice.

How to think about the plan

  1. The function rates ONE reading and returns one label. The for loop in the main program calls it once per reading.
  2. Each branch returns. return ends the function, so only the first true branch counts.
  3. Order matters: check 11 first, then 8, 6, 3. If you checked 3 first, an 11 would say Moderate.
  4. Pass one reading at a time, not the whole list.

Think first

  • What goes in, and what comes back?
  • In what order should the conditions go, and why?
  • Where does the for loop go: inside the function or in the main program?

def uv_advice(uv):
    if uv >= 11:
        return "Extreme: stay in the shade"
    elif uv >= 8:
        return "Very high: sunscreen and a hat"
    elif uv >= 6:
        return "High: sunscreen"
    elif uv >= 3:
        return "Moderate: sunglasses"
    else:
        return "Low: enjoy the beach"

readings = [11, 7, 9, 2, 4]
for uv in readings:
    print("UV", uv, "->", uv_advice(uv))

Watch out

Calling uv_advice(readings) with the whole list stops with TypeError: '>=' not supported between instances of 'list' and 'int'. Pass one reading per loop pass.

An MDC student logs Metrobus commute times to the Kendall campus, in minutes, in the list given in the plan. Write average_minutes(times) that uses a for loop to add up the times, then returns the total divided by how many times there are. Print the result with 1 decimal, like this: Average commute: 42.0 minutes

How to think about the plan

  1. Same shape as calculate_average_price from class: a total that starts at 0, a for loop that adds, and a return AFTER the loop.
  2. len(times) tells you how many times there are, so you don't have to count them yourself.
  3. Watch the indent of the return. Inside the loop, it would leave after the first time.
  4. Put the call inside an f-string and format it with :.1f.

Think first

  • What does the total start at, and where does it start?
  • What does each loop pass add?
  • Why must the return line up with the for, not with the line inside it?

def average_minutes(times):
    total = 0
    for t in times:
        total += t
    return total / len(times)

commutes = [42, 35, 51, 38, 44]
print(f"Average commute: {average_minutes(commutes):.1f} minutes")

Watch out

If the return is indented inside the loop, the function leaves after the first time and prints 8.4 (42 divided by 5) instead of 42.0. An empty list stops with ZeroDivisionError: division by zero.
